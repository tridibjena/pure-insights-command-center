## How the data is structured

The file has no timestamp. `report_id` takes only 100 distinct values and each appears exactly
20 times, in the same order on every pass. The pipeline therefore treats the *n*-th occurrence of a
report as its *n*-th **snapshot**. The metrics are monthly/30-day aggregates (`monthly_active_views`,
`query_count_last_30d`). Their lag-1 autocorrelation between consecutive passes is ≈ 0 (see forensic check 1), so the
passes are consecutive, non-overlapping 30-day periods — monthly snapshots — not rolling daily windows. The calendar anchor
is the last complete month before the data was received: snapshot 1 = 2025-02 to snapshot 20 = 2026-09
(configurable via `DATA_AS_OF_MONTH`). `report_name` is constant per report (verified); `owner_email` is not.

## 7 · Forensic checks

Each structural observation about the dataset raises a question the data itself can answer. These checks are recomputed by
`python -m pic_pipeline.cli forensics` and stored in `app.dq_forensics` (shown on the Data Quality page).

### 1 · Snapshots are consecutive, non-overlapping 30-day periods

* **Question.** The CSV has no timestamp and repeats each report 20 times. Are the passes daily rolling 30-day windows (heavily overlapping) or separate periods?
* **Method.** Lag-1 autocorrelation of each 30-day metric between consecutive passes of the same report. Rolling daily windows share 29/30 of their data, so they would correlate near +0.97.
* **Result.** Mean lag-1 autocorrelation: monthly_active_views -0.027, query_count_last_30d -0.023, credits_clean -0.083, aws_hosting_cost_usd -0.048
* **Conclusion.** No overlap between passes: each pass is an independent 30-day period, i.e. a monthly snapshot.
* **Treatment.** 20 monthly snapshots ending at the last complete month before the data was received (2026-09); series 2025-02 → 2026-09. Anchor configurable via DATA_AS_OF_MONTH.

### 2 · Report identity explains none of the variance

* **Question.** Do some reports persistently have more views, cost or latency than others, or is each row an independent draw?
* **Method.** One-way ANOVA of each metric by report_id with a 2,000-shuffle permutation p-value.
* **Result.** monthly_active_views F=0.83 p=0.88, credits_raw F=1.11 p=0.19, avg_load_time_sec F=1.16 p=0.14, aws_hosting_cost_usd F=1.12 p=0.21, query_count_last_30d F=1.04 p=0.37
* **Conclusion.** No metric differs between reports more than chance (all p ≥ 0.05): rows behave like independent draws, so per-report rankings (slowest reports, highest cost per view, decommission candidates) are not statistically distinguishable from noise in this dataset.
* **Treatment.** Portfolio-level findings are stated as findings; per-report rankings are presented as a demonstration of the method, which is valid on real data where report identity does carry signal.

### 3 · Owners — and orphaning — are assigned independently each month

* **Question.** Reports average 10.2 different owners over 20 months. Are these hand-offs (sticky ownership) or random assignment? Does orphaning persist?
* **Method.** Probability that a report keeps the previous month's owner, compared with the probability two independent draws from the owner pool coincide; same comparison for orphan status.
* **Result.** P(same owner as previous month) = 0.065 vs 0.072 for independent draws (14 owners, each 5.7%–8.3%); P(orphaned | orphaned previous month) = 0.104 vs base rate 0.122.
* **Conclusion.** Ownership and orphaning carry no month-to-month memory: the churn is random reassignment in the source data, not a pattern of hand-offs.
* **Treatment.** The latest snapshot is the system of record for the current owner (14 reports currently orphaned); the full owner history is kept for the drill-down and every orphaned report-month counts towards unowned spend.

### 4 · UNKNOWN refresh status is a telemetry gap, not a hidden failure

* **Question.** 100 rows report UNKNOWN. Do they behave like failures (e.g. follow failed refreshes, slower loads) or like missing telemetry?
* **Method.** Rate of UNKNOWN right after a FAILED/TIMED_OUT month vs its base rate; mean latency, credits and views for UNKNOWN vs other rows; spread across reports and snapshots.
* **Result.** P(UNKNOWN | previous month failed) = 0.048 vs base 0.050; UNKNOWN vs others — avg_load_time_sec 27.1 vs 27.9, credits_clean 592.8 vs 611.4, monthly_active_views 673.9 vs 755.7; spread over 66 reports, 2–9 per snapshot.
* **Conclusion.** UNKNOWN is unrelated to failures or performance: it is missing telemetry scattered across the portfolio.
* **Treatment.** Not counted as a refresh failure; raises a TELEMETRY_GAP warning so the monitoring gap itself is visible.

### 5 · Anomalies were injected independently; overlaps are chance or arithmetic

* **Question.** 3 negative-credit rows are also orphaned and 4 of 4 zero-view months carry Snowflake credits. Are the defects linked?
* **Method.** For each of the 28 pairs of anomaly flags, observed overlap vs the overlap expected if independent, with a hypergeometric p-value (Bonferroni threshold 0.05/28).
* **Result.** negative credits ∧ orphaned: 3 observed vs 2.94 expected (p=0.58); 98.8% of all rows carry credits and credits do not track views (r=+0.048); pairs significant after correction: zero_view_cost ∧ peak_exceeds_views (4 vs 0.19), peak_exceeds_views ∧ aws_cost_per_view_outlier (65 vs 6.28).
* **Conclusion.** The negative-credit/orphan overlap is exactly what chance predicts, and zero-view months carry credits because almost every row does. The only significant pairs are arithmetic: zero views make any peak exceed views, and very low views drive both the impossible-usage and the cost-per-view outlier flags.
* **Treatment.** Each defect keeps its own rule and register entry; overlapping rows are handled by every applicable rule (e.g. RPT_201 #20 is quarantined for credits and nulled for ownership).
