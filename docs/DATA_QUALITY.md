## How the data is structured (and the one modelling assumption)

The file has no timestamp. `report_id` takes only 100 distinct values and each appears exactly
20 times, in the same order on every pass. The pipeline therefore treats the *n*-th occurrence of a
report as its *n*-th **snapshot**. The metrics are monthly/30-day aggregates (`monthly_active_views`,
`query_count_last_30d`), so each snapshot is mapped to a 30-day billing period, snapshot 1 = 2025-01 to snapshot 20 = 2026-08.
`report_name` is constant per report (verified); `owner_email` is not (see *Ownership churn*).

## 3 · Extreme load-latency spikes (up to 55 s)

* Observed range **0.60 s to 55.00 s** (median 27.8 s, p95 52.1 s).
  **6 rows sit exactly at the 55.00 s maximum.**
* **The alert threshold is 15 s (strictly greater than), from Task 2.** 55.00 s is the extreme of the
  injected spikes, *not* a threshold. 7 rows are exactly 15 s and correctly do **not** alert.
* Spikes are **kept unchanged** — never capped, winsorised or removed — because a 55-second dashboard load is a real
  operational event and is exactly what the real-time alerting must catch. Only invalid readings (non-numeric, ≤ 0 or
